Guests

The guest side of a range definition: hosts, images, and the content they carry, from accounts and services to defense and Active Directory.

Overview

Guests are the virtual machines in a range. They come in three kinds: hosts (the targets), routers (gateways between network segments), and the attacker. In a definition, “host” on its own always means a target, not the physical machine the range runs on. This page covers the guest half of a range definition. Network addressing, segmentation, and routing are covered in Networks.

Defining guests comes first (hosts, images, resources, routers, the attacker), then guest content and the sections that produce and vary it, then how configuration reaches a guest.

Hosts

Hosts are the machines the attacker works against: web servers, databases, domain controllers, workstations. Each host entry declares the guest’s identity (its name and, optionally, its in-guest hostname and FQDN), its operating system, the image it boots from, its CPU and memory, and the networks it attaches to. What runs on the host (accounts, services, weaknesses, data) is declared separately, under Guest content.

This example defines a single host:

  • YAML
  • Python
range:
  name: hosts
  description: Host identity fields and what consumes them.

networks:
  - name: corp
    cidr: 10.20.0.0/24
    mode: isolated

hosts:
  - name: dc01
    hostname: dc01-nyc
    fqdn: dc01.corp.example
    os: { type: linux, distro: ubuntu-24.04 }
    image: acme/dc-golden
    resources: { cpus: 2, memory_mb: 4096 }
    interfaces: [{ network: corp, ip: 10.20.0.5 }]

attacker:
  interfaces: [{ network: corp }]
  entry: external
1
The definition-wide identifier (exec targets, ACL endpoints).
2
The in-guest hostname, when it differs from name.
3
The fully qualified name, for ranges whose DNS serves it. 
from inspect_ranges.types import (
    Attacker, Host, Interface, Network, Os, RangeMeta, RangeSpec,
    Resources,
)

hosts = RangeSpec(
    meta=RangeMeta(
        name="hosts",
        description="Host identity fields and what consumes them.",
    ),
    networks=[
        Network(name="corp", cidr="10.20.0.0/24", mode="isolated")
    ],
    hosts=[
        Host(
            name="dc01",
            hostname="dc01-nyc",
            fqdn="dc01.corp.example",
            os=Os(type="linux", distro="ubuntu-24.04"),
            image="acme/dc-golden",
            resources=Resources(cpus=2, memory_mb=4096),
            interfaces=[Interface(network="corp", ip="10.20.0.5")],
        )
    ],
    attacker=Attacker(
        interfaces=[Interface(network="corp")], entry="external"
    ),
)

Python definitions import from inspect_ranges.types (shown once above, later Python tabs omit it).

name is how everything else refers to the guest: sandbox("dc01") in evaluations, ACL endpoints, DNS authoritative lists. hostname is only needed when the in-guest name should differ, and fqdn matters for domain-joined ranges. os records the platform (type: linux | windows, with distro or version detail); interfaces are covered in Networks.

The in-guest hostname is the declared hostname: when one is present, else a hostname-safe form of name: invalid characters such as underscores and dots become hyphens, and Windows names truncate to the 15-character NetBIOS limit. Two guests whose rendered hostnames collide refuse at planning. fqdn is set at build time by the Active Directory recipes, so a range declaring it refuses to run until a build has produced that content and recorded it in the build manifest (see Building Ranges).

roles tags a host’s function, such as roles: [domain-controller, dns] or [member-server]. The tags tell the build what a host is for and give scoring a way to refer to hosts by function rather than by name. Roles take effect through the host’s provisioning recipes at build time; a host declaring roles but no recipe refuses at planning (realized-section-unconsumed).

Nested Virtualization

A host that runs KVM virtual machines of its own (a kernel-under-test workload, an appliance emulated inside the guest) declares it:

  • YAML
  • Python
hosts:
  - name: bench
    image: ubuntu-noble
    nested_virtualization: true
    interfaces:
      - { network: lab }
Host(
    name="bench",
    image="ubuntu-noble",
    nested_virtualization=True,
    interfaces=[Interface(network="lab")],
)

The declaration is held, never assumed: planning refuses it under a named cpu_model (only the default host-passthrough carries the virtualization flag into guests), and up refuses at preflight unless the host’s KVM module exposes nesting (the doctor nested kvm row reports it). The guest image still loads its own kvm modules. Without the declaration, guests may still run software emulation (QEMU TCG), which needs no host support.

Images

Every host names the image it boots from. Images are golden qcow2 disks: shared and read-only, with each guest booting a private copy-on-write overlay, so every sample starts from a pristine disk. A golden carries the baked-in control daemon plus whatever the scenario installed at build time. The definition references images by name, and planning resolves each reference against the local image cache to a sha256 digest. How bare names resolve beyond the cache (pins, registries, the public catalog) is covered in Images.

An image reference missing from the cache shows up in the plan output and is an error at render:

✗ range.yaml  1 error
  12:5  hosts[0].image  image 'acme/db-golden' for guest 'db' is
                        not in the image cache, so the bundle
                        cannot be self-sufficient (pull or build
                        the image into the cache)

Resources

Sizing is backend-neutral and optional:

  • YAML
  • Python
resources:
  cpus: 2
  memory_mb: 4096
  disk_gb: 20
Resources(cpus=2, memory_mb=4096, disk_gb=20)

Omitted resources resolve to 1 vCPU, 1024 MiB, and a 10 GiB overlay. The defaults suit an idle service host; a guest that compiles from source at build time (Period Software) or runs a database wants 2 vCPUs and 2048 MiB. inspect-ranges plan reports the range’s totals (guests, vCPUs, memory) so a deployment can admission-check before anything boots.

Hardware

Most images boot under the engine’s standard machine shape (q35 chipset, SeaBIOS, virtio NICs and disks, no video device). Images built against particular virtual hardware, appliances above all, declare what they need in a hardware block whose every default reproduces the standard shape exactly, so an absent block changes nothing:

  • YAML
  • Python
hosts:
  - name: fw
    image: acme-fw
    hardware:
      firmware: uefi
      machine: pc
      nic_model: e1000
      video: vga
      disks:
        - { source: acme-fw-data, bus: ide }
        - { size_gb: 5 }
    interfaces:
      - { network: lab, ip: 10.0.0.10 }
Host(
    name="fw",
    image="acme-fw",
    hardware=Hardware(
        firmware="uefi",
        machine="pc",
        nic_model="e1000",
        video="vga",
        disks=[
            HardwareDisk(source="acme-fw-data", bus="ide"),
            HardwareDisk(size_gb=5),
        ],
    ),
    interfaces=[Interface(network="lab", ip="10.0.0.10")],
)

  • firmware: bios (default), uefi (OVMF with a per-guest nvram copy), or uefi-secure (the MS-key-enrolled OVMF build with SMM, q35 only: the Windows 11 contract). tpm: true adds an emulated TPM 2.0 (a per-guest swtpm libvirt manages; its state is per-boot, so images must not seal disk secrets to it, and the guest’s VMM runs as the shared libvirt-qemu principal rather than a per-VM uid: libvirt holds the swtpm control socket at 0600 to its owner. The plain consequence: TPM guests are not isolated from one another at the VMM layer, so prefer one TPM guest per range). Windows guests take exactly these two knobs; the rest of the block stays the Windows tier’s own.

  • machine: q35 (default) or pc (i440fx), for images built against the older chipset.

  • nic_model: virtio (default) or e1000, for images without virtio drivers or whose configs key to emulated Intel NICs. Images that key behavior to a specific MAC address can declare one per interface (mac: "52:54:00:ab:cd:ef", unique within the range).

  • video: a vga device, when the image needs one. Load-bearing beyond graphics: the VGA device occupies a PCI slot, and some images’ network configs depend on the resulting NIC slot ordering.

  • disks: extra disks after the root, each a blank volume (size_gb) or a copy-on-write overlay of a cache image (source, which resolves like any image reference and must be in the cache at render). The guest sees virtio extras from vdc (vda is the root, vdb stays reserved for the seed slot so device names never shift) and ide extras from hda. The ide bus requires machine: pc (q35 has no IDE controller; refused hardware-ide-requires-pc).

The block parameterizes the QEMU domain only: cloud-hypervisor guests refuse it (hardware-vmm-not-supported), and Windows guests take firmware and tpm alone, with the rest of their measured device model owned by the Windows tier (hardware-windows-not-supported). A Windows 11 host (os: { type: windows, version: "11" }) must declare the full contract, hardware: { firmware: uefi-secure, tpm: true } (the shape its golden installs under), and refuses windows11-hardware-required without it.

Appliances

A sealed appliance (a router OS, a firewall VM, anything consumed as a vendor artifact) cannot carry the control daemon, so the engine never reaches inside it. Such a guest boots an imported image as-is and is declared opaque:

  • YAML
  • Python
hosts:
  - name: fw
    image: acme-fw
    opaque: true
    readiness: { tcp: 443 }
    interfaces:
      - { network: lab, ip: 10.0.0.10, mac: "52:54:00:ab:cd:ef" }
Host(
    name="fw",
    image="acme-fw",
    opaque=True,
    readiness=TcpReadiness(tcp=443),
    interfaces=[
        Interface(network="lab", ip="10.0.0.10", mac="52:54:00:ab:cd:ef")
    ],
)

Opaque is a contract, enforced fail-closed on both sides:

  • Nothing reaches inside. An opaque guest carries no content sections (provisioning, services, data, defense, and the rest all refuse; users stays legal as documentation of baked-in accounts), gets no seed disk, and is never the attacker’s foothold. In-guest scoring verbs refuse with the tier named, and the exec witness records a declared capability drop. Score an appliance externally (network, liveness) or through a managed operator guest beside it.

  • Addresses are declared facts, not instructions. Every interface of an opaque guest must declare its ip: the address is baked into the image, and the engine cannot invent one (opaque-ip-required). On a dhcp: true network the declared MAC and ip become the appliance’s reservation, so a DHCP-client appliance leases its baked address deterministically.

  • Readiness is observed, not reported. With no daemon handshake, readiness says how up decides the guest is ready: {tcp: <port>} probes a TCP connect against the first declared address, and process (the default) means the VM process runs. An appliance whose stack boots slowly declares its budget alongside the port ({tcp: 830, timeout: 1200}), extending the shared window for that guest. readiness on a non-opaque guest refuses.

Routers

A router is an ordinary guest with one interface per joined segment, running a generated firewall that a defender inside the range can inspect. os and image are optional; when omitted, the backend’s default router appliance is used. A router can also be a target in its own right: it takes users and provisioning like a host, built and captured on the same path as host content (Building Ranges). A router declaring content must declare image as well (router-image-required), since the appliance default is a backend resolution its build key cannot pin. For example:

  • YAML
  • Python
range:
  name: router-guest
  description: >
    A router with explicit identity, and one with backend defaults.

networks:
  - name: dmz
    cidr: 10.80.10.0/24
    mode: isolated
  - name: internal
    cidr: 10.80.20.0/24
    mode: isolated

routers:
  - name: edge
    os: { type: linux, distro: ubuntu-24.04 }
    image: acme/router-golden
    resources: { cpus: 1, memory_mb: 512 }
    interfaces: [{ network: dmz }, { network: internal }]
    acl:
      - { from: dmz, to: internal, allow: [tcp/443] }

hosts:
  - name: app
    os: { type: linux }
    image: acme/app-golden
    interfaces: [{ network: internal }]

attacker:
  interfaces: [{ network: dmz }]
  entry: external
router_guest = RangeSpec(
    meta=RangeMeta(
        name="router-guest",
        description="A router with explicit identity, and one with "
        "backend defaults.",
    ),
    networks=[
        Network(name="dmz", cidr="10.80.10.0/24", mode="isolated"),
        Network(
            name="internal", cidr="10.80.20.0/24", mode="isolated"
        ),
    ],
    routers=[
        Router(
            name="edge",
            os=Os(type="linux", distro="ubuntu-24.04"),
            image="acme/router-golden",
            resources=Resources(cpus=1, memory_mb=512),
            interfaces=[
                Interface(network="dmz"),
                Interface(network="internal"),
            ],
            acl=[
                AclRule(from_="dmz", to="internal", allow=["tcp/443"])
            ],
        )
    ],
    hosts=[
        Host(
            name="app",
            os=Os(type="linux"),
            image="acme/app-golden",
            interfaces=[Interface(network="internal")],
        )
    ],
    attacker=Attacker(
        interfaces=[Interface(network="dmz")], entry="external"
    ),
)

Policy (acl) and routing (routes, gateway election) are covered in Networks.

Attacker

The attacker is a guest like any other, declared separately because evaluations treat it specially (it is what sandbox("default") resolves to). It either boots as a dedicated attack box or starts from a foothold on a declared host. A dedicated attack box declares interfaces; name defaults to attacker, and omitting image selects the catalog’s attack, a kali-class toolset image pulled automatically at eval init (its tool contract and boot defaults are on Attack Box):

  • YAML
  • Python
range:
  name: attack-box
  description: A dedicated attack box with explicit sizing.

networks:
  - name: dmz
    cidr: 10.80.10.0/24
    mode: isolated

hosts:
  - name: web
    os: { type: linux }
    image: acme/web-golden
    interfaces: [{ network: dmz }]

attacker:
  name: kali
  image: acme/kali-golden
  resources: { cpus: 2, memory_mb: 4096 }
  interfaces: [{ network: dmz }]
  entry: external
attack_box = RangeSpec(
    meta=RangeMeta(
        name="attack-box",
        description="A dedicated attack box with explicit sizing.",
    ),
    networks=[
        Network(name="dmz", cidr="10.80.10.0/24", mode="isolated")
    ],
    hosts=[
        Host(
            name="web",
            os=Os(type="linux"),
            image="acme/web-golden",
            interfaces=[Interface(network="dmz")],
        )
    ],
    attacker=Attacker(
        name="kali",
        image="acme/kali-golden",
        resources=Resources(cpus=2, memory_mb=4096),
        interfaces=[Interface(network="dmz")],
        entry="external",
    ),
)

A dedicated attack box runs under Cloud Hypervisor by default, so the most adversarial guest gets the smaller VMM (see Security). Declare vmm: qemu to keep QEMU; with host: set, the foothold host’s own vmm applies. Hosts and routers default to QEMU and opt in with vmm: cloud-hypervisor.

With host:, the attacker declares no machine of its own (the foothold is the machine), and entry: assumed-breach records the premise. The foothold is an ordinary declared host, so it carries provisioning: recipes and other guest content like any host; the build lifts the attacker’s egress containment for the build only (Building Ranges). The attacker’s egress posture is covered in Networks.

A dedicated attack box can carry provisioning: recipes of its own, built and captured like a host’s (Building Ranges). A provisioned attack box must declare image: (attacker-image-required): the standard attack image default is a backend resolution the build key cannot pin. Its recipes run last in the build order, with build egress. Recipes must keep the agent user and the daemon’s unprivileged default identity: readiness refuses an attack box whose daemon reports root (Attack Box).

  • YAML
  • Python
range:
  name: provisioned-attacker
  description: A dedicated attack box with its own tooling recipe.

networks:
  - name: dmz
    cidr: 10.80.10.0/24
    mode: isolated

hosts:
  - name: web
    os: { type: linux }
    image: acme/web-golden
    interfaces: [{ network: dmz }]

attacker:
  image: ubuntu-noble
  interfaces: [{ network: dmz }]
  entry: external
  provisioning:
    - { recipe: acme.attack-tools }
provisioned_attacker = RangeSpec(
    meta=RangeMeta(
        name="provisioned-attacker",
        description="A dedicated attack box with its own tooling recipe.",
    ),
    networks=[
        Network(name="dmz", cidr="10.80.10.0/24", mode="isolated")
    ],
    hosts=[
        Host(
            name="web",
            os=Os(type="linux"),
            image="acme/web-golden",
            interfaces=[Interface(network="dmz")],
        )
    ],
    attacker=Attacker(
        image="ubuntu-noble",
        interfaces=[Interface(network="dmz")],
        entry="external",
        provisioning=[ProvisioningStep(recipe="acme.attack-tools")],
    ),
)

Guest Content

Beyond identity and sizing, a definition declares what a guest contains: accounts, services, seeded weaknesses, planted files, and protections. These declarations describe the converged state of a guest, not boot-time actions. Each declaration is realized at build time and the range ships verified; the runtime never applies guest content per sample.

inspect-ranges build converges nothing itself: the range’s recipes create the accounts, write the files, and seed the weaknesses (Authoring Recipes). The build then independently verifies every declared services and vulnerabilities entry against the live guests and captures each guest’s disk as a realized image. Declared users, misconfigurations, and data are not independently probed yet: the build trusts the recipes for them, and behavioral checks confirm whichever the attack chains depend on. Routers carry content too, realized by their provisioning recipes. A range declaring content refuses planning (range-not-built) until a matching build exists; once one does, the range boots those captured images. scheduled_activity realizes at build too: each declaration installs as a persistent unit in the captured image and is verified afterward (Scheduled Activity).

Users

users declares a guest’s local accounts: the recipe creates them, and the declaration records the converged state. Routers take users the same way, realized by their own provisioning recipes (a router declaring users without a recipe refuses at planning, realized-section-unconsumed, because nothing would realize them). Domain accounts belong in active_directory, not here:

  • YAML
  • Python
range:
  name: users
  description: Local accounts as converged state.
networks:
  - name: lab
    cidr: 10.10.10.0/24
    mode: isolated
hosts:
  - name: server
    os: { type: linux }
    image: acme/server-golden
    interfaces: [{ network: lab }]
    users:
      - { name: alice, password: bacon, note: "weak password" }
      - name: backup
        groups: [sudo]
        note: service account with sudo
attacker:
  interfaces: [{ network: lab }]
  entry: external
users = RangeSpec(
    meta=RangeMeta(
        name="users", description="Local accounts as converged state."
    ),
    networks=[
        Network(name="lab", cidr="10.10.10.0/24", mode="isolated")
    ],
    hosts=[
        Host(
            name="server",
            os=Os(type="linux"),
            image="acme/server-golden",
            interfaces=[Interface(network="lab")],
            users=[
                User(
                    name="alice",
                    password="bacon",
                    note="weak password",
                ),
                User(
                    name="backup",
                    groups=["sudo"],
                    note="service account with sudo",
                ),
            ],
        )
    ],
    attacker=Attacker(
        interfaces=[Interface(network="lab")], entry="external"
    ),
)

Services

services entries are assertions about the guest’s converged listening surface, not an installation language. The build satisfies them (through a recipe, the image, or a checkpoint) and verifies them: the named service is listening on the declared port at the declared version. Installation itself belongs in provisioning. The optional package names the dpkg package that embodies the service, for version attribution when the listening process cannot provide it. The verification contract is in Building Ranges:

  • YAML
  • Python
range:
  name: services
  description: >
    The converged listening surface, asserted and build-verified.
networks:
  - name: lab
    cidr: 10.10.10.0/24
    mode: isolated
hosts:
  - name: web
    os: { type: linux }
    image: acme/zabbix-golden
    interfaces: [{ network: lab }]
    services:
      - { name: zabbix-web, port: 80, version: 3.0.3 }
      - name: mysql
        port: 3306
        version: "5"
        credentials: { user: root, password: root }
attacker:
  interfaces: [{ network: lab }]
  entry: external
services = RangeSpec(
    meta=RangeMeta(
        name="services",
        description="The converged listening surface, asserted and "
        "build-verified.",
    ),
    networks=[
        Network(name="lab", cidr="10.10.10.0/24", mode="isolated")
    ],
    hosts=[

Planted Data

data declares scenario files: targets worth finding or exfiltrating, supporting material, captures. Nothing creates or verifies a data: file: the recipe writes the ones that should exist on the image. An exfiltrate goal’s file is planted per sample by the challenge layer (the recipe creates only its parent directory). Flags never appear here; the per-sample secrets belong to challenges:

Defense

The range-level defense section records the defensive posture on the D0 (no defenders) to D5 (adaptive defender) spectrum, with telemetry flows where signals are recorded or forwarded. A posture realizes through its telemetry flows, so a tier declared without telemetry entries refuses at planning; omitting defense already means D0. Per-host toggles turn individual protections on or off:

Provisioning References

Scheduled Activity

scheduled_activity declares recurring in-guest behavior: bot scripts and scheduled tasks that create the user and defender activity real tradecraft depends on. The build realizes each declaration as a persistent unit in the captured image: a systemd service (plus a timer for interval schedules) on Linux, a scheduled task on Windows. Every boot of the captured image runs the activity on its schedule, with no per-sample work.

script is a relative path resolved from the activities/ directory beside range.yaml. Its content digest enters the guest’s build key, so an edited script rebuilds exactly the guests that declare it. A Linux script needs a shebang; a Windows script runs through powershell -NoProfile -ExecutionPolicy Bypass -File. schedule accepts @boot (once per boot) and every <N><unit> where <unit> is s, m, or h (for example every 5m); a seconds interval on Windows refuses at build, since its task scheduler repeats at one-minute granularity. The activity runs as the declared user, or as root/SYSTEM when omitted. After realization the build verifies each unit or task exists and is enabled:

  • YAML
  • Python
range:
  name: activity
  description: Behavior simulation on a domain controller.
networks:
  - name: corp
    cidr: 10.20.0.0/24
    mode: isolated
hosts:
  - name: dc01
    os: { type: windows, version: server-2022 }
    image: windows-2022
    interfaces: [{ network: corp }]
    scheduled_activity:
      - { script: responder.ps1, schedule: "every 1h" }
      - script: rdp_scheduler.ps1
        schedule: every 15m
        user: admin.user
        note: creates a stealable session
attacker:
  interfaces: [{ network: corp }]
  entry: assumed-breach
activity = RangeSpec(
    meta=RangeMeta(
        name="activity",
        description="Behavior simulation on a domain controller.",
    ),
    networks=[
        Network(name="corp", cidr="10.20.0.0/24", mode="isolated")
    ],
    hosts=[
        Host(
            name="dc01",
            os=Os(type="windows", version="server-2022"),
            image="windows-2022",
            interfaces=[Interface(network="corp")],
            scheduled_activity=[
                ScheduledActivity(
                    script="responder.ps1", schedule="every 1h"
                ),
                ScheduledActivity(
                    script="rdp_scheduler.ps1",
                    schedule="every 15m",
                    user="admin.user",
                    note="creates a stealable session",

Variables

variables declares values intended to differ between instances of the same range: ports, passwords, flag hints. Every variable requires a default, and loading substitutes the defaults before validation.

A variable marked draw: boot also gets a per-sample value, drawn when the sample’s range boots. The draw comes from the declared constraints (port/int from min/max, choice from choices). The drawn values are written to /etc/guestd/draws.json in every Linux guest’s cloud-init seed; the agent’s foothold is excluded, since a drawn value is often a challenge’s expected answer. Applying a draw is the range author’s job: a recipe installs a boot unit that reads the file and reconfigures the service (kypo_demo moves telnetd to the drawn port this way). Everything else keeps the default: realized images and build keys never change with a draw. draw: boot requires type port, int, or choice; a password variable refuses it, and text has no constraints to draw from. An answer goal naming a drawn variable scores the drawn value.

References are "{{name}}": a whole-scalar reference keeps the variable’s type (port: "{{telnet_port}}" validates as an integer) and embedded references interpolate as text. Substitution covers every scalar in range.yaml, and only range.yaml: challenges.yaml never substitutes, and a goal reads a variable by name instead. A reference naming no declared variable is a positioned undeclared-variable error. In Python there is no substitution; the pattern is a plain function whose parameters play the role of the references:

  • YAML
  • Python
range:
  name: randomized
  description: A randomized service port and a templated credential.
variables:
  telnet_port: { type: port, min: 1500, default: 2323, draw: boot }
  admin_password: { type: password, default: "changeme123!" }
networks:
  - name: lab
    cidr: 10.10.10.0/24
    mode: isolated
hosts:
  - name: server
    os: { type: linux }
    image: acme/server-golden
    interfaces: [{ network: lab }]
    users:
      - { name: admin, password: "{{admin_password}}" }
    services:
      - { name: telnetd, port: "{{telnet_port}}" }
attacker:
  interfaces: [{ network: lab }]
  entry: external
def randomized(
    telnet_port: int = 2323, admin_password: str = "changeme123!"
) -> RangeSpec:
    return RangeSpec(
        meta=RangeMeta(
            name="randomized",
            description="A randomized service port and a templated "
            "credential.",
        ),
        variables={
            "telnet_port": Variable(
                type="port", min=1500, default=2323, draw="boot"
            ),
            "admin_password": Variable(
                type="password", default="changeme123!"
            ),
        },
        networks=[
            Network(name="lab", cidr="10.10.10.0/24", mode="isolated")
        ],
        hosts=[
            Host(
                name="server",
                os=Os(type="linux"),
                image="acme/server-golden",
                interfaces=[Interface(network="lab")],
                users=[User(name="admin", password=admin_password)],
                services=[Service(name="telnetd", port=telnet_port)],
            )
        ],
        attacker=Attacker(
            interfaces=[Interface(network="lab")], entry="external"
        ),
    )


spec = randomized()

Guest Configuration

The range compiler emits each guest’s desired configuration (addressing, resolvers, hostname, the router’s firewall); how it reaches the guest is a per-image capability. Linux guests inject over cloud-init (a read-only virtio seed disk). Windows hosts inject over a per-boot unattend seed: a read-only cdrom whose answer file drives the sysprep’d golden’s specialize pass, with readiness announced by the control daemon. Since that addressing is always static, a Windows guest on a dhcp: true network never takes a lease and is configured statically anyway (validation warns windows-dhcp-static). Windows routers are not yet realized and refuse at planning. An attack box is always Linux. A Windows host declaring vmm: cloud-hypervisor refuses at planning, since the seed rides removable media Cloud Hypervisor cannot present. Other injectors are designed but not yet implemented.

  • Python

Windows 11 clients ride the same tier: os: { type: windows, version: "11" } with image: windows-11 and the hardware contract declared (hardware: { firmware: uefi-secure, tpm: true }). The golden installs through images derive-windows --os 11 from the same two user-supplied, sha256-pinned ISOs, under the contract itself: the installer VM boots the MS-key secure loader with SMM and an emulated TPM 2.0, lays the disk out GPT with an ESP, and selects the Pro image with the documented edition-selection key. Everything else behaves exactly as on server goldens: the unattend specialize seed, daemon readiness, and exec as SYSTEM are proven on a Windows 11 clone, and recipes and plants ride that same daemon channel.

On Windows the default exec identity is SYSTEM: the contract user root maps to the daemon’s own identity, and root is not a Windows principal. An explicit user runs under that account’s own logon. The daemon reads that account’s credentials from C:\guestd\users.txt, one name:password line per account, so a recipe that wants named-user exec creates the account and writes that file. The pre-capture scrub deletes the file: the daemon credential file never rides a realized disk. A realized image that needs named-user exec when consumed re-creates the file at boot, for example from an @boot activity running as SYSTEM.
