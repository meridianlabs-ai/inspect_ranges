## Unreleased

- Builds gate each Windows guest's first recipe on setup completion (a new `oobe-settle` stage beside `network-settle`). On a client's first boot from a sysprepped golden, OOBE keeps running about ten minutes past daemon readiness, and its completion step silently undoes exactly the work recipes do in that window: it clears the LSA `DefaultPassword` secret and resets account and logon material, so an autologon or account a recipe set up vanished before capture (measured). The gate polls `ImageState` until `IMAGE_STATE_COMPLETE` (20-minute bound, `oobe_settle` and `oobe_settle_timeout_s` build options) and is instant on realized images and servers, whose state is already complete.

- `doctor` reads installed (Windows) goldens against the Windows install recipe version instead of misreading them as stale against the Linux recipe version, gives a stale Windows golden its own re-derive guidance, and skips imported images, which have no recipe to compare against.

- The readiness failure names each failed guest's own probe window. A guest's declared boot budget extends the shared window, so reporting only the shared number misstated how long a slow guest was actually given.

- Client Windows goldens bake Windows Update off at install: the `NoAutoUpdate` policy plus disabled `wuauserv`/`UsoSvc` start. On client media WU patches and auto-restarts at variable times, which kills builds mid-recipe and makes clone content drift with the patch cadence. The Windows install recipe version moves to 5 (existing goldens re-derive on next use); servers keep their stock behavior.

- The range container image can draft off the configured registry: with `INSPECT_RANGES_RANGE_IMAGE` unset and `INSPECT_RANGES_REGISTRY` explicitly set, `up` resolves the location's convention name `range` at the engine-version tag (a tag inside a single-repository location, the hub form's `<name-prefix>-range` repository (exactly the catalog's published name), or `<prefix>/range` elsewhere) and uses the digest it resolves to, never the mutable tag, so the no-mutable-tag posture holds end to end. The explicit pin always wins; the default search path never drafts (a pin-less dev host keeps building locally); a missing convention ref logs the attempt and falls back to the local build. One registry value now configures a fleet completely.

## 0.2.13 (02 November 2026)

- `hardware: {firmware: uefi-secure, tpm: true}` is realized: Secure Boot guests get the MS-key-enrolled OVMF build (`secure='yes'`, SMM on, per-guest nvram copied from the enrolled VARS template, q35 only, refused `hardware-secure-requires-q35` otherwise) and `tpm` adds a per-guest swtpm 2.0 the range container's libvirt manages (state is per-boot: nothing may seal disk secrets to it). Windows guests now accept exactly these two knobs, the Windows 11 contract, while the rest of the hardware block stays refused there (the tier owns its measured device model). The range image gains `swtpm` (run as libvirt-qemu:kvm; a TPM guest's QEMU runs as that shared principal instead of a per-VM uid, since libvirt holds the swtpm control socket at 0600 to its owner and the hardened container has no relabel slot; the trade stated plainly: TPM guests are not isolated from one another at the VMM layer, so a VMM escape in one reaches every other TPM guest's process, disk, emulated TPM, and the swtpm local CA (non-TPM guests keep their per-VM-uid bound, and nothing is agent-reachable without that escape first)). Verified live: an ubuntu guest under the enrolled keys reports SecureBoot enabled from its own efivars and exposes a working TPM 2.0 at /dev/tpm0.

- Windows 11 goldens: `images derive-windows --os 11` installs a Windows 11 client golden through the same one-shot hardened flow, under the contract setup verifies (q35, the MS-key secure loader with SMM, an emulated TPM 2.0, a GPT/ESP disk layout, w11 virtio drivers, the Pro image selected by index with the documented edition-selection key); the OS variant enters the derivation key, and the install bound is a per-variant fact. The installer answers every measured client-OS trap: boot-prompt keypresses gate on the install cdrom's read counter (a stray space presses setup's Cancel and a quit-confirm modal blocks the restart), the OOBE wizard is skipped outright, `BypassNRO` covers the deliberately network-less install VM, device encryption is prevented at both registry points (sysprep refuses an encrypting volume), and the client's DISABLED built-in Administrator activates and takes its password at specialize (so cmd-hostile admin passwords refuse up front). Verified live: a clone boots the production pipeline and reports Secure Boot enabled, the TPM ready, and the Pro edition from inside the guest, with exec as SYSTEM over vsock. A `version: "11"` Windows host must declare `hardware: { firmware: uefi-secure, tpm: true }`, the shape its golden installs under (refused `windows11-hardware-required` otherwise). Windows golden sidecars now record `kind: installed` explicitly rather than riding the `.iso`-suffix fallback, and the daemon bundle's Windows installer selects its virtio driver directory by the running OS (client w11, server 2k22; the daemon bundle version bumps in lockstep).

- `oracle.alive(guest)`: VMM-process liveness for any guest, daemon-managed or opaque, observed from the driver (`virsh domstate` for QEMU guests, the recorded pidfile for Cloud Hypervisor ones) through a seam every oracle-reaching construction path injects (the provider, `range_oracle` attach, and the build's proof boot). The denial-of-service scoring primitive: goal types can now assert an appliance died or survived without any in-guest access. QEMU states `paused`, `pmsuspended`, and `in shutdown` count as alive (a reversible nap is deliberately not a kill, so an in-guest suspend cannot game a DoS goal); Cloud Hypervisor pidfiles are verified against the process's comm so pid recycling cannot read alive-when-dead. Unknown guests refuse; a missing seam refuses rather than guessing (unit fixtures, and separated host backends, where the range's docker is remote and a local probe would read every guest dead); failure to observe reads as not-alive, never an exception, which also means an externally realized attack box reads not-alive (goals score appliances, not the attack box).

- The exec witness (per-guest `execve` evidence) is hardened and its record made honest. The daemon now accepts only genuine kernel process-connector messages (sender `nl_pid` 0), so an in-guest process — even as root — can no longer forge `execve` records through it; combined with the daemon's unprivileged-by-default execution identity, an agent must first earn root (itself witnessed) before it can interfere. A daemon restart is now detected by a boot-session change carried on every `exec_events` reply, closing a window where a restart whose sequence had already passed the cursor went unrecorded. A kernel subscriber overflow (`ENOBUFS`) is recorded as an unknown-size gap rather than a false event count (the kernel reports overflow episodes, not lost events); a ring overwrite keeps its exact count. Event `ts_ms` is documented as the host-ingest wall-clock time it has always been (not the connector's monotonic timestamp). The `exec_events_result` reply carries an optional `session` field (protocol unchanged, optional on decode); the daemon version is `3.5.0` (also reconciling the bundle label, which trailed the daemon at `3.3.0`).

- The guest daemon (`vsockd`) now fails closed instead of silently running the agent as root when it cannot drop to the unprivileged `agent` user. Default-identity exec and file operations on a root daemon whose image is missing the `agent` account are refused (`EACCES`) rather than run with root's reach; an explicit `user=` is unaffected, and an unprivileged daemon (dev/CI, no root to hand out) stays tolerant. The pong reply additionally reports the daemon's default-exec identity, and `up` refuses a dedicated attack box (the foothold) whose daemon would run the agent as root — a privilege-escalation task must not start already solved. A daemon predating the new pong field reports no identity and is left to the daemon's own guard. Protocol version is unchanged (the field is optional on decode); the daemon version is `3.4.0`.

- `up --from-spec` and the attack-box conformance battery (`inspect-ranges attackbox verify`) no longer require the attacker's image in the cache when a provider supplies the attack box (`INSPECT_RANGES_ATTACK_BOX`). Both render the bundle to a temporary directory and realize it once with the provider already resolved, which boots the dedicated attack box instead of pulling its image locally, so the self-sufficiency cache check previously forced a download the run never used. The check still holds for every other guest and for bundles `inspect-ranges render` writes, which may later run without a provider and must stay self-sufficient.

- Isolated `dhcp: true` networks now advertise the bridge's service address as a dead-end router option in every lease: some appliance DHCP clients refuse to program a lease that carries no router option (observed live porting a management-plane appliance whose client logged `dhcp-address-assigned` and then installed nothing). The address answers nothing and routes nowhere, so isolation is unchanged; this is the same lease shape libvirt and slirp present. Linux guests on such segments gain a dead-end default route they previously lacked.

- Attack box: an external provider can be a pinned program rather than an installed Python package (`INSPECT_RANGES_ATTACK_BOX=inspect_ranges._attackbox.pinned.pinned_attack_box:<pin file>`). A deployment-written pin file names one release by tag, source-tarball URL, and SHA-256; the first use downloads the tarball, verifies the digest before extracting anything, caches the release per user, and runs `<program> attackbox boot|teardown|probe` over a versioned JSON protocol with the tap fds passed at the numbers the request names. Eval init fetches and probes beside the catalog image pull and refuses with the program's own cause and remedy when the host cannot boot a box; the recorded origin carries the pin's contents, not its path, so `down` and the reaper tear a box down with the release that booted it. `INSPECT_RANGES_ATTACK_BOX_PROGRAM` names an installed copy for offline hosts. The default is unchanged: with the variable unset, the realizer boots the built-in box.

## 0.2.6 (31 October 2026)

- Fixes a 0.2.5 regression that failed every range boot on common kernels: the bridged-frames accepts used `meta ibrname`/`obrname` in the `inet` family table, and bridge meta is bridge-family-only on most kernels, so `nft -f` refused the ruleset ("Operation not supported") and the range container exited before anything booted. ## 0.2.5 (31 October 2026)

- The normalized spec hash excludes defaulted values: adding a schema field whose default reproduces prior behavior no longer moves any existing spec's hash, so build manifests, published builds, and default project names survive vocabulary-widening engine upgrades. The soundness rule ships with it: defaults are frozen contracts (a shipped default's meaning never changes; new behavior arrives behind a new field or an explicitly declared `schema_version`), pinned by a recorded snapshot of every shipped default and a golden hash of a canonical spec. One-time migration: this change itself moves every spec hash once (existing build manifests read `range-not-built` until their ranges rebuild, and the published examples republish with this release), after which schema additions stop paying that cost.

- Hosts can declare `nested_virtualization: true` (the guest runs KVM virtual machines of its own, e.g. kernel-under-test workloads). Thanks to the default-insensitive normalized form (above), the new field moves no existing spec hash; a bundle that declares the flag needs this engine or newer (older engines refuse its `boot.json` fail-closed), while undeclared new bundles stay readable by older engines (the flag is emitted only when set).

- New command `inspect-ranges shell <project> [guest]`: an interactive operator shell on a guest of a running range, as a tmux session driven entirely over the range's control channel, so it needs no SSH and no guest listener and works on fully isolated networks. Guest output is treated as untrusted and filtered before it reaches the operator's terminal (clipboard-write and palette OSC sequences and all device-control strings are dropped; display sequences and titles pass). Sessions survive detach (`Ctrl-]`) for reattach by the same name; `--user` picks the guest identity (default: the daemon identity, root on Linux); `--cast` records the attach as a local asciicast. Linux guests only. The provider's `connection()` message now points operators at `shell` instead of a recorded follow-up.

- Range networking on hosts with `br_netfilter` loaded (Docker hosts, Amazon Linux among them): frames bridged within one segment were diverted through the range namespace's default-drop forward chain, since every new network namespace starts with `bridge-nf-call-iptables=1`, so same-segment guests could resolve each other's addresses but exchange no IPv4 packet (an attack box saw every target port filtered). The forward chain now accepts a frame that enters and leaves through the same segment bridge, one rule per bridge, ahead of the egress policy; a routed frame has at most one bridge side and still meets that policy.
